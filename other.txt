Good context. Let me walk through what I see before suggesting anything.                                                                                                        
                                   
  What the Code is Currently Doing                                                                                                                                                
                                                                                                                                                                                  
  The convert() method processes lines sequentially:                                                                                                                              
  line 1 → parseLine() → doStuff() → transform() → out.write()                                                                                                                    
  line 2 → parseLine() → doStuff() → transform() → out.write()                                                                                                                    
  ...
  line 1000 → ...

  One line at a time, single thread, for every file.

  Where Parallelism Could Help

  transform() is the interesting one — it does a lot of work (building lists, constructing objects) and touches no shared state. It takes inputs and produces an output. That's
  the ideal candidate for parallelization.

  The problem is out.write(). That output stream is shared, so multiple threads writing to it simultaneously would corrupt the output.

  The Two Realistic Options

  Option 1 — Parallel stream, synchronized write

  Java's parallelStream() is a low-effort switch, but you'd need to synchronize the write:
  reader.lines()
        .map(line -> parseLine(line))
        .parallel()                           // transform() runs on multiple threads
        .forEach(jsonObj -> {
            synchronized (outStream) {        // serialize the writes
                doStuff(jsonObj, outStream);
            }
        });
  The tradeoff: threads could finish transforms out of order, so output order is not guaranteed.

  Option 2 — Parallel transform, sequential write (cleaner)
  reader.lines()
        .map(line -> parseLine(line))
        .parallel()                           // transform() on multiple threads
        .map(jsonObj -> transform(jsonObj, template, otherObjFactory))
        .sequential()                         // switch back to single thread
        .forEach(obj -> outStream.write(obj)); // one thread writes
  This keeps output ordered and avoids locking entirely.

  ---
  The Bigger Win: File-Level Parallelism

  You mentioned "tons of JSON files." If each file is processed by a single thread right now, you're leaving a lot of performance on the table. An ExecutorService lets you
  process multiple files concurrently:

  ExecutorService pool = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());

  for (File file : files) {
      pool.submit(() -> convert(file.inputStream(), file.outputStream()));
  }

  pool.shutdown();
  pool.awaitTermination(Long.MAX_VALUE, TimeUnit.SECONDS);

  Each file gets its own input/output stream, so there's no shared state between files — no synchronization needed. This is likely the biggest speedup.

  ---
  Before Parallelizing, One Question

  Is otherObjFactory thread-safe? If createOtherObj() has any internal mutable state (counters, caches), multiple threads calling it simultaneously could race. template looks
  read-only but worth verifying too. If either has mutable state, you'd either need to synchronize access or give each thread its own instance.

  What does otherObjFactory actually do under the hood?









 If the factory is cheap to construct and its state is per-conversion (not global), you can instantiate one per thread:

  reader.lines()
        .map(line -> parseLine(line))
        .parallel()
        .map(jsonObj -> {
            OtherObjFactory localFactory = new OtherObjFactory(); // no sharing
            return transform(jsonObj, template, localFactory);
        })
        .sequential()
        .forEach(obj -> outStream.write(obj));

  Option 2 — Synchronize access to the factory

  If constructing the factory is expensive, share it but lock around it:

  synchronized (otherObjFactory) {
      otherObjFactory.createOtherObj(1, false, "someName", "someVal");
  }

  The downside is that this serializes all factory calls, potentially negating the benefit of parallelism if factory calls are a significant portion of the work.

  Option 3 — Make the factory stateless

  The cleanest long-term fix. If the ordering check used the first argument to validate against the list being built locally in transform() rather than state stored inside the
  factory, the factory would have nothing to share between threads. Whether this is feasible depends on how deeply the ordering logic is embedded in the factory.
